# Diagnostic

Owner: Huy. Go/Echo/pgx with domain/application independent of infrastructure.

Implemented scope: DI-002–011 and the patient-owner path of DI-013. LAB_TECH can collect/reject/recollect, enter drafts and submit complete results; LAB_REVIEW can return results for rework or publish them after the two-person check. Published-result events contain identifiers and publication metadata only. Patient owners can read paginated PUBLISHED results with a current DI-013 lease. Staff detail remains separate from patient access. Every write requires a UUID Idempotency-Key; retries must use the same key and body. DI-001 is documented in OpenAPI as private and disabled by default; no public recovery POST is registered.

DI-003, DI-012 and the doctor path of DI-013 use the Clinical-owned `VisitDoctorGrantChanged` stream. A missing or stale checkpoint or an observed sequence gap returns 503 on the doctor path. DI-013 filters by the doctor's authorized visits before pagination. A signed visit retains read access unless revoked. DI-012 requires a current Identity lease, a visit open for cancellation, successful settlement and no specimen. The order shows `PENDING_SYNC` until Billing projects `REQUESTED`, `FAILED` or `SUCCEEDED`.

For the group demo, load Huy's `DIAGNOSTIC_DATABASE_URL` as `DATABASE_URL`: it must select `diagnostic_db` on Neon with `sslmode=require`. Run `go run ./cmd/migrate` before `go run ./cmd/api`. Configure LISTEN_ADDR, JWT_ISSUER, JWT_AUDIENCE and JWT_PUBLIC_KEY_FILE from the shared Identity key pair. JWT verification uses RS256 and the service's access projection; missing Identity configuration fails closed. Health readiness confirms schema, not external integration readiness.

Run `go run ./cmd/worker` with the same online DATABASE_URL and `RABBITMQ_URL` set to Quân's `UMC_AMQP_URL` (`amqps://`). DIAGNOSTIC_DECLARE_TOPOLOGY=1 declares only Diagnostic-owned exchanges/queues and binds to already provisioned source exchanges. Shared topology remains the infrastructure owner's responsibility. Worker uses manual ACK, durable retry/dead-letter storage, mandatory publisher confirmations and transactional outbox. A process crash after publish may redeliver; the transaction inbox and requestId guard prevent repeated business effects.

The `000002_visit_subjects` migration moves the patient mapping out of the stored order body into `diagnostic_visit_subjects`. It backfills existing orders in one transaction and fails if a visit is associated with multiple patients or a required ID is missing or invalid. Verify and correct conflicting source data before retrying. Stop old Diagnostic API and worker instances before migrating, then start both from the new version. The HTTP response and cross-service message fields `visitId` and `patientId` keep the same meaning and shape.

CreateLabOrder is accepted only from Clinical command exchange and expected routing key. Canonical requestHash is SHA256 of the Go JSON map containing requestId,visitId,patientId,doctorId,testSnapshot,authorizedAt (sorted map keys). Unit/referenceRange are included even when empty. One clinical request creates one order, one charge request and LabOrderResolved atomically. Price data comes from the local Catalog projection at authorizedAt. Catalog sequence gaps or checkpoints older than30seconds block new charges. Unavailable projections remain retryable; they do not fabricate payment or an accepted order.

The trusted bootstrap command `go run ./cmd/import-projections` reads JSON array from stdin. Each entry has kind,key,value,version. Kinds: access,patient,TEST,DOCTOR,LAB_PRICE,catalog. Entity keys are UUIDs; catalog key is checkpoint. Access value is `{userId,actorType,status,tokenVersion,capabilities}`. Patient value is `{ownerUserId,active}`. DOCTOR value is `{identityUserId}`. TEST value contains id,code,name,unit,referenceRange,revision,status. LAB_PRICE value contains itemId,itemType=LAB,priceVersionId,revision,amountVnd,effectiveFrom,effectiveTo?. Catalog checkpoint contains sequence,at. This operator tool is not exposed as an HTTP endpoint; imports require increasing versions and reject conflicting same-version content. CatalogChanged and access messages subsequently update the normal projections.

Collection requires local ChargePrepared and a matching successful settlement fence from trusted Billing messages. FAILED decisions leave a tombstone even before reserve. UNKNOWN and timeouts keep the lock. The worker emits QuerySettlement every30seconds for locked orders. Reject keeps specimen history and audit identity; recollect creates a new specimen/sequence/barcode on the same order and never requests a new charge. Barcodes remain unique after rejection. Result drafts, review, publication and owner reads use immutable order-test snapshots and do not leak result values to Clinical.

Billing topics are shared by LAB, Appointment and Pharmacy. Diagnostic records non-LAB ChargePrepared/ChargePaid events in its inbox without changing LAB data or scheduling retries. SettlementDecision currently has no sourceType: decisions whose sourceId is absent from Diagnostic orders are acknowledged as foreign. This relies on the normal causal chain: the LAB order commits before its RequestCharge reaches Billing. Restore Diagnostic's owned orders before replaying payment history after a database restore. Storage errors still retry; explicit LAB charge evidence with a missing order still retries. Decisions for existing LAB orders retain the fence and terminal-state checks above.

Verification: `go test ./...`, `go vet ./...`, `go build ./...`; on Windows run `python tools/huy/test_postgres.py --service diagnostic` for the isolated PostgreSQL HTTP/lifecycle suite and actual OpenAPI response fixtures. The Diagnostic integration writes the real `LabResultPublished` envelope; `python tools/huy/test_postgres.py --service clinical` consumes it through Clinical's receiver when that fixture exists. Broker tests use `-tags=brokerintegration` and an isolated TEST_RABBITMQ_URL. CI validates both result-response fixtures against the OpenAPI contract and runs the cross-service wire test.

Integration boundary: current repository's Catalog full entity/checkpoint publisher and live Identity/Billing handoffs must be available for a full team journey. Trusted bootstrap supports local verification but is not evidence of the complete group Gate3. No HTTP calls to Billing or cross-service database access are used.

## Cancellation evidence for Billing

DI-012 now returns `data.cancellationId`; pass this UUID as BI-007 `sourceId` (not the LAB order ID). Authorized DI-003 detail reads expose the same optional field for a CANCELLED order, so a lost response can be recovered through HTTP. Missing/invalid owner evidence fails closed; no replacement cancellation ID is invented.

An identical cancellation retry checks current Identity, lease and read grant before returning its stored result. Signing the visit prevents a new cancellation but does not discard an already successful response. Revoking the grant still blocks both detail and replay. Older stored replay responses are hydrated from the existing owner cancellation record without creating another event. No Diagnostic migration is required for this response change. Billing remains the refund owner.

## Local Docker and delivery/cache model

Run `python tools/be/run.py` from the repository root. It starts the entire group project with the existing three owner env files and online databases, RabbitMQ and Redis. Web: http://127.0.0.1:15173; Gateway uses the port in Quân’s env. No replacement credentials, keys or demo database are generated.

The API applies pending migrations at startup only when `MIGRATE_ON_START=1`, then exposes readiness. `/api healthcheck` reuses the binary for Docker health checks. Manual `/migrate` uses the API image with an overridden entrypoint and `--rm`; no separate migrate service is kept. The RabbitMQ worker remains a separate process and waits for API readiness.

Retries are durable RabbitMQ deliveries handed off through outbox, with bounded prefetch and NotBefore/token/attempt validation. Failure handoff goes to RabbitMQ DLQ through outbox. The new runtime does not query retry_jobs or dead_letters. Stop old binaries before applying the broker delivery migration. Legacy orphaned retry inbox entries are preserved as LEGACY_RETRY_ORPHANED DLQ handoffs; when the old job/body is missing, historicalBodyUnavailable is explicit. They are not automatically replayed.

`REDIS_URL` (or native fallback `UMC_REDIS_URL`) configures the shared Redis endpoint. Diagnostic cache uses `umc:diagnostic:v1:*`, TTL 30 seconds and a database-derived record version. Current database permissions and authorization leases are checked before every cache read. Redis failure or malformed cached data falls back to PostgreSQL. Draft data, tokens and settlement decisions are never cached.
