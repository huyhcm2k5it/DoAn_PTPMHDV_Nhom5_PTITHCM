# Diagnostic: order and specimen integration

Implemented boundary: DI-002–011 and the PATIENT-owner path of DI-013 in `diagnostic.openapi.json`. DI-012 is registered but fails closed until the Appointment-owned current doctor/visit grant projection is supplied. DOCTOR access to DI-013 is likewise unavailable until a current grant projection exists. DI-001 recovery creation remains disabled and absent from the public contract.

The doctor submits CL-005 to Clinical. Its transaction commits the pending registry and `CreateLabOrder` outbox together. Diagnostic consumes that command from `umc.commands.clinical.v1`, routing `diagnostic.create-lab-order.v1`; it does not accept patient identity, prices or paid status from the browser. The immutable test definitions are verified against its local Catalog projection. Price versions and patient ownership must already be projected locally.

One transaction deduplicates the clinical request, creates the order, writes `RequestCharge` for Billing and emits `LabOrderResolved` for Clinical. HTTP 202 from Clinical remains pending until the actual result is received. Retries must preserve request ID/hash; conflicting content is rejected. The canonical request hash is SHA-256 of Go JSON encoding of a map containing requestId, visitId, patientId, doctorId, testSnapshot and authorizedAt (keys sorted, hash excluded).

Billing must send `ChargePrepared`, perform `ReserveSettlement`/`SettlementReserved`, and supply a matching terminal decision/payment event. A charge ID alone does not allow collecting a specimen. The owner checks source revision, amount hash, settlement ID and fence. UNKNOWN keeps the source locked; FAILED tombstones prevent a late reserve from relocking it. Locked settlements are queried periodically through outbox, without an HTTP call to Billing.

LAB_TECH can collect, reject with reason/version, and recollect. Recollection retains the order/charge and increments the specimen sequence; barcodes are unique. LAB_REVIEW reads the queue/detail. DOCTOR detail requires a current Appointment-owned visit grant; this projection is not yet supplied, so doctor detail currently fails closed with 503. Patient access is excluded from these staff endpoints.

The web feature accepts the team's authenticated transport. Route registration and session management remain in their existing owner modules. The standalone preview proxies Diagnostic to localhost:8009; it does not create accepted claims or successful payments.

Run `tools/huy/test_diagnostic_postgres.py` for the isolated native PostgreSQL suite. CI runs PostgreSQL plus RabbitMQ adapter tests. Shared Gate 3 additionally requires the actual Identity, Appointment and Billing services, Gateway routes, broker ACLs and a clean Compose journey; local fixtures do not establish that whole-group result.

Catalog now publishes versioned full-snapshot entity changes and stream checkpoints. Diagnostic consumes that feed, detects gaps/stale checkpoints, and fails closed before creating a new charge. Trusted Catalog snapshot import remains an operator-only bootstrap/reconciliation path; it is not a public endpoint and does not replace the live feed. Do not advance a production checkpoint manually to make a payment pass.

## DI-007–013: result lifecycle, cancellation and patient reads

Result writes retain the existing order/specimen representation and store a separate versioned result object in Diagnostic. DI-007 selects the latest active `COLLECTED` specimen on the order; the request contains `items[]` with `testCode`, `valueText` and optional `unit`, `referenceRange`, `flag`. `testCode` must exist exactly once in the immutable order snapshot. Unit and reference range are sourced from that snapshot; optional client copies are accepted only when equal. A draft may be incomplete, but DI-009 requires every ordered test exactly once before REVIEW.

DI-008 requires `expectedVersion` and accepts only DRAFT/REWORK; each successful edit appends the actor to the revision contributor history. DI-009 requires LAB_TECH and moves a complete result into REVIEW. DI-010 requires LAB_REVIEW, a nonempty reason and expectedVersion and returns REVIEW to REWORK. DI-011 requires LAB_REVIEW, expectedVersion and an authorization lease; it atomically publishes only when the reviewer is absent from contributors. PUBLISHED revisions are immutable. Every mutation requires a UUID Idempotency-Key and replays only the original request hash/response.

`LabResultPublished` has metadata only (`orderId`, `visitId`, result `revision`, `publishedAt`, `recipientUserId`, order `version`); it never carries values, units, reference ranges or clinical text. `LabCancelled` carries `orderId`, `visitId`, stable `cancellationId`, `noSpecimen=true`, `reasonCode` and order `version`. See `../messages/lab-lifecycle.v1.schema.json`. Billing consumes the cancellation event and owns void/refund. Diagnostic returns `PENDING_SYNC` until a versioned Billing status projection is received; it never claims a refund succeeded from the cancellation command alone.

Compatibility decision: persisted and existing `state` values stay unchanged (`PENDING_PAYMENT`, `SPECIMEN_COLLECTED`, `SPECIMEN_REJECTED`, etc.). The additive `lifecycleState` exposes canonical aliases `WAITING_PAYMENT`, `SAMPLING`, and `RECOLLECT_REQUIRED` for those three values. Existing messages are accepted only through the producer/routing aliases already deployed; new Catalog events use lowercase `catalog` and `catalog.catalog-changed.v1`. `DI-001` remains disabled and is not registered in OpenAPI or public Gateway.

DI-012 requires a current doctor/visit ownership projection, authorization lease, expectedVersion and reasonCode. It serializes with collect/recollect/reserve under the order transaction and checks the complete specimen history. Cancellation is accepted only for an order whose charge and settlement are both confirmed paid, and before any specimen is collected; pending/prepared charges and active settlements are rejected so a delayed `ChargePrepared` cannot race a cancellation. Any historical specimen, including REJECTED, permanently blocks cancellation. A repeated key/cancellation cannot emit a second refund basis. The production PostgreSQL adapter does not yet have the Appointment-owned grant projection, so this endpoint currently returns 503 and fails closed. Billing remains responsible for refund execution/status; Diagnostic keeps `PENDING_SYNC` until a versioned Billing status projection is integrated.

DI-013 supports the PATIENT owner with an active PatientAccess projection and current read lease. It returns only PUBLISHED results, ordered by publication time and stable ID using page/limit; it never exposes DRAFT, REVIEW, REWORK or contributor history. The DOCTOR path currently returns 503 until the owner supplies a current revocable doctor/patient grant projection. Result response bodies are `no-store` and are excluded from application logs.

For wire verification, Diagnostic integration captures the actual `LabResultPublished` outbox envelope and DI-013 response. Clinical consumes the captured envelope through its production receiver in a separate PostgreSQL integration test. The CI job validates the actual response bodies against this OpenAPI contract. These tests prove the two owned adapters' wire compatibility; they do not prove the live Appointment grant or Billing refund status handoffs.
